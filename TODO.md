# Gotato TODO

Open defects and design decisions, verified against the code. Planned capabilities (one writer per Session across instances, the warm Session and its TTL, fault injection and the multi-instance harness) and the *Later* list (MCP, rate-limit info, examples and more) are tracked in [FEATURES.md](FEATURES.md). Remove an item in the commit that resolves it.

## Defects

- [ ] **An output-limit continuation starts a new Round.** With `MaxTruncatedContinuations` above 0 (it is 0 by default), a reply cut off at the output limit is followed by `UserMessage(TruncatedContinuationText)` (`loop.go`, `limits.go`). The gateway's `roundStart` (`gateway/provider.go`) takes any user Message as the start of a Round, so Claude and OpenAI are no longer sent the cut reply's reasoning, which the model needs to go on. Read from the code, not run. Fixed by FEATURES.md → G-F29, where the continuation becomes a `continue` notice.

- [ ] **A writer of a deleted Record can append to the Record created again.** `Store.Append` in `MemoryStore` (`session/memory.go`) and `FileStore` (`session/file.go`) compares only the length (the file store, its head cache and a file named for the next position). A writer that loaded a Record, which was then deleted and created again at the same length, appends to the new Record, and the new Record's Summary names the old epoch. With two processes on one file store, a position can be written twice when the batches do not line up. It is older than the epochs, and `testkit/storetest` does not check it. Verified by scratch tests on both stores and an end-to-end Runner test, not kept. Fix: an epoch-conditional `Append` (refuse with `ErrNotFound` when the stored epoch differs from the writer's), a file store head cache and batch check that know the epoch, and a `storetest` check.
- [ ] **An open or a create can cut a valid stream of a newer Record.** `open` and `create` (`service/liveness.go`) write their claim, then call `cutStreams`, and `markStreams` (`service/streams.go`) cuts every started stream whose epoch is not the opener's. If the Record is deleted and created again on another instance between the claim and `cutStreams`, and a client starts a stream of the new Record on this instance in that gap, the stream ends with `cannot_resume`. The window is microseconds and needs that delete and create inside it; the client recovers by starting over. Verified by a scratch test that holds the claim's `Append`, not kept. Fix: cut only the streams registered before the open began its `Load` (a generation taken then), and mark the others for one more `Load` instead of cutting them.

## Decisions

- [ ] **Where a Recap goes when no user Message follows it.** A Segment's header and its Recap are tagged text in the adjacent user Message (FEATURES.md → G-F29). After an idle compaction, a `Continue` without a prompt, or a FollowUp, leaves the last Recap with no user Message after it. Chat Completions has no system message mid-conversation to fall back on, and a user Message made for it would start a Round, which notices were designed to avoid. Options: a user message on the wire that the Record keeps as a notice, so it starts no Round; or a native form where the provider has one and the tagged form in that message otherwise. Recommendation: settle it in G-F29's forms, as one rule for a notice and a Segment's tags with no user Message after them.
- [ ] **ToolSet activation is not a fact.** `toolset_activated` is a log entry, not among the facts `session/entry.go` lists, and activation lives only in the live Session's registry (`toolset.go`). Nothing reads it back, and the Runner builds a live Session for every Run (`run` in `service/service.go`), so today a ToolSet the model switched on is gone at its next Run, on any instance. Read from the code, not run. The design keeps the active ToolSets in each Checkpoint, so between two compactions an instance that loads the Session offers only the ToolSets of the last Checkpoint, while the warm instance offers more, against DESIGNS.md → The Context depends only on the Record and the Agent. The limit is older than Segments, but compaction now relies on the active set. Options: make activation a fact a rebuild reads; or keep the limit as FEATURES.md → G-F06 and G-F10 state it. Recommendation: make activation a fact.
- [ ] **What `--keep N` and `CompactPolicy.Floor` mean with Segments.** Today `gotato context compact <id> --keep N`, `{"keep":N}` on `POST /v1/sessions/{id}/compact`, and `CompactPolicy.Floor` (`modelctx/compact.go`) set how much recent history a compaction keeps. With Segments, each compaction closes everything since the last Checkpoint, and keeps a tail only mid-Run, sized by its own setting. The CLI and HTTP fields are part of the versioned contract. Options: keep them as the size of the kept tail; or remove them, with a CHANGELOG note. Recommendation: keep them as the size of the kept tail, so the contract does not break.
- [ ] **The compaction record holds the Recap call's usage, not its cost.** The approved draft asks for both. Gotato keeps no prices: the model catalog is in FEATURES.md → Later, and DESIGNS.md → Every number about a Run comes from Events and `Usage`. So FEATURES.md → G-F06 records the usage of the model call that wrote the Recap, from which its cost follows. Options: usage only; or a cost too, once the model catalog has prices. Recommendation: usage only, until the model catalog exists.
