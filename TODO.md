## Defects

- [ ] **An output-limit continuation starts a new Round.** With `MaxTruncatedContinuations` above 0 (it is 0 by default), a reply cut off at the output limit is followed by `UserMessage(TruncatedContinuationText)` (`loop.go`, `limits.go`). The gateway's `roundStart` (`gateway/provider.go`) takes any user Message as the start of a Round, so Claude and OpenAI are no longer sent the cut reply's reasoning, which the model needs to go on. Read from the code, not run. Fixed by FEATURES.md → G-F29, where the continuation becomes a `continue` notice.

- [ ] **A writer of a deleted Record can append to the Record created again.** `Store.Append` in `MemoryStore` (`session/memory.go`) and `FileStore` (`session/file.go`) compares only the length (the file store, its head cache and a file named for the next position). A writer that loaded a Record, which was then deleted and created again at the same length, appends to the new Record, and the new Record's Summary names the old epoch. With two processes on one file store, a position can be written twice when the batches do not line up. It is older than the epochs, and `testkit/storetest` does not check it. Verified by scratch tests on both stores and an end-to-end Runner test, not kept. Fix: an epoch-conditional `Append` (refuse with `ErrNotFound` when the stored epoch differs from the writer's), a file store head cache and batch check that know the epoch, and a `storetest` check.
- [ ] **An open or a create can cut a valid stream of a newer Record.** `open` and `create` (`service/liveness.go`) write their claim, then call `cutStreams`, and `markStreams` (`service/streams.go`) cuts every started stream whose epoch is not the opener's. If the Record is deleted and created again on another instance between the claim and `cutStreams`, and a client starts a stream of the new Record on this instance in that gap, the stream ends with `cannot_resume`. The window is microseconds and needs that delete and create inside it; the client recovers by starting over. Verified by a scratch test that holds the claim's `Append`, not kept. Fix: cut only the streams registered before the open began its `Load` (a generation taken then), and mark the others for one more `Load` instead of cutting them.

## Decisions

- [ ] **A Session stops at 1,000 messages by default.** `CoreLimits.MaxMessages` (default 1,000) bounds the whole Transcript, not one Run. Once a Session holds 1,000 messages, every later Run fails with `limit_exceeded` when it commits the prompt, unless the Session is compacted or the service raises the limit. Automatic compaction is off by default, so a long-lived Session reaches this without warning. Options: count only the Run's own messages, raise the default, or document the limit next to compaction (`limits.go`, `commitMessage` in `session.go`). The reference workload raises the limit for `history_1000` (`testkit.HistoryTask`). The maintainer's view (2026-10-18): the count of messages is not what matters, the size of the Context is, and a Context that grows too large should be compacted; so this is settled with how a Session is compacted (G-F06, ROADMAP.md → Waiting for design).
