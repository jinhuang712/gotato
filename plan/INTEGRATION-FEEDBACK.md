# Integration feedback: first real adoption (a Lark bot service running on several pods)

Source: the downstream team's append-only log (entries `D-001` to `D-012`; the team calls them G-NNN, renamed here so they do not clash with GOALS.md goals). Each entry was checked against this repository on 2026-10-29. The log is still growing: add new entries below, do not rewrite old ones.

Verdict: **confirmed** (the claim holds), **partly** (part of it holds, see the note), **wrong** (the repository already covers it).

Remove an item from *Backlog* in the commit that resolves it, as in [TODO.md](TODO.md).

## Backlog

### P0

- [ ] **D-009 · The `WithForwarding` example can be bypassed.** Verdict: confirmed, but the risk is in the example, not the docs. `nil` allow forwards nowhere and redirects are not followed, and the docs say so. The example uses `strings.HasPrefix(address, "http://10.0.")`, which `http://10.0.evil.com` passes. `serve --forward` allows every address; its code comment says "test tool", its help text does not. Fix: parse the URL and check the host IP against a CIDR (or an instance allow-list) in the example and in `guides/http-in-five-minutes.md`; say "tests only" in the `--forward` help.
- [ ] **D-001 · Release order and proxy warm-up.** Verdict: partly, now healed. Tags and module paths are right. The root tag `v0.2.0` was made 20 seconds before `adapter/mcp/v0.2.0`, and proxy.golang.org likely cached "not found" for a few minutes, so `go get` reported "found, but does not contain package". It no longer reproduces. The downstream team later confirmed it by measurement: the proxy served the module again within about an hour, and a clean-cache `go mod download` and their CI passed. Fix: in the release notes, tell the releaser to run `go get` once in a clean module cache after tagging and to announce only when it passes; push nested-module tags first (or together), then warm the proxy with a `.info` request; document that a new nested tag can lag by minutes, and that `GOPROXY=direct` is the fallback.

### P1

- [ ] **D-004 · An MCP server without annotations hides every tool under `WithMaxEffect`.** Verdict: confirmed (docs only; the core's `WithMaxEffect` code was not read). `WithToolEffect` matches the exact MCP name only. Fix: add `WithDefaultEffect(ToolEffect)` for tools with no annotations, or `WithToolEffectFunc`; add the consequence to the MCP section of FEATURES.md.
- [ ] **D-002 · `adapter/mcp` cannot filter or rename tools.** Verdict: confirmed. The only cleaning is empty and repeated names, recorded in `Skipped()`. Fix: `WithToolFilter(func(*sdk.Tool) bool)` (rejected tools go to `Skipped` as "filtered") and `WithToolRename(func(string) string)`; add both to the options table.
- [ ] **D-006 · A streamed card across pods needs the card's id, and nothing says so.** Verdict: partly. Deltas are sent, not stored; a slow subscriber skips only deltas; `StreamSession` on another instance sees no deltas. Wrong in the log: the card is updated by the writer's own `SubscribeInstance`, so the *message* id need not be shared; what a writer switch needs is the **card's** own id. `examples/larkbot` stores only the thread root. Fix: one sentence in FEATURES.md "deltas are visible only on the writer Instance"; a streaming card in the example (buffer by RunID, throttle about 500 ms, store the card id in Session metadata, final text from `RunEnded` when `events_skipped` fires).
- [ ] **D-007 · `larkbot` does not de-duplicate across pods.** Verdict: confirmed. Wrong in the log: `examples/larkbot/README.md` and a test already call it a known gap; the two guides do not mention it. Fix: copy the README note into `guides/example-chat-bot.md` and `guides/embed-in-a-service.md`; pass Lark's `message_id` as `MessageRequest.RequestID` so a repeat can be found in `run_started`. Gotato itself does not de-duplicate `RequestID` in 0.2.0 (roadmap item).

### P2

- [ ] **D-003 · Nothing warns against `http.Client.Timeout` on the MCP transport.** Verdict: partly. Headers are covered by a `RoundTripper` (FEATURES.md says so), but no text says that `Client.Timeout` cuts the standalone SSE stream, and the `WithHTTPClient` comment invites setting a timeout. Fix: one sentence in the option comment and FEATURES.md (use `Transport.ResponseHeaderTimeout` and the Run's context). Optional: `WithHeaders(func(ctx) http.Header)`.
- [ ] **D-008 · No Mongo guidance for a custom `session.Store`.** Verdict: partly. The requirements hold (atomic batch plus head update, unique `(id, seq)`, epoch rule, 24 backing stores). Wrong in the log: `storetest` has an epoch case that names the rule, and later abilities can come as optional interfaces. Fix: add a Mongo section to `guides/write-a-store.md` (unique index, `E11000` to `ErrConflict`, epoch in the head document's filter, replica set for a transaction or a head-document CAS otherwise).
- [ ] **D-010 · Reasoning effort cannot be set through a self-hosted gateway on chat/anthropic wires.** Verdict: partly. `refuseReasoningConfig` rejects it on both; only Responses sends it. Wrong in the log: an unrecognised host already returns every reasoning artifact, so no `provider: deepseek` is needed. Fix: document how to set `provider` for a LiteLLM host (cache TTL optimizations need it); consider a pass-through extra body field.
- [ ] **D-005 · No cost field or price table.** Verdict: confirmed, and a gap in the docs, not a stated non-goal. Fix: say in FEATURES.md that cost is the team's own conversion of `Usage`; add a worked example. No core change.

### New since the first pass

- [ ] **D-013 · No guide shows a streaming card, and the example uses `SubscribeInstance`, not `StreamRun`.** Verdict: partly. The downstream claim holds: a `StreamRun` sink gets every Event of the Run (deltas, `tool_started`, `tool_ended`, `tool_progress`), and no other Instance sees them. Not so: the docs never say "use `StreamRun` for a streaming card" (`guides/` only uses it to collect Events in tests), and `examples/larkbot` uses `SubscribeInstance` because a message sent into a running Run is queued there and its caller gets no sink. This refines D-006: a card needs `StreamRun` (or `StreamSession`), and a queued message has no deltas. Fix: a "streaming card" section in `guides/example-chat-bot.md` with that limit.
- [ ] **D-014 · `guides/write-a-store.md` does not say how to run `storetest` without a database.** Verdict: partly. Wrong in the log: `storetest.Run` needs no external service and no transaction; `MemoryStore`, `FileStore` and the guide's `mystore` all pass it, and the contract is one conditional write with a unique `(id, seq)`. A multi-document transaction is a cost of the Mongo design chosen, not a Gotato rule. Follow-up from the downstream team (measured): their Mongo Store passed all 30 `storetest.Run` subtests, also with `-race -count=5`, on a single-node replica set started in user space (MongoDB 8.0, official tarball, `mongod --replSet`, one `replSetInitiate`; no Docker or package manager). Not covered: multi-node, transaction retry on failover, several pods writing one Session. Fix: a "no database at hand" section (point to the three above and `storetest.Check`); a CI example that starts a real backing store; say that a single-document atomic write plus the unique key is enough. Write down the user-space replica-set steps above; for Mongo implementers this is the biggest obstacle.
- [ ] **D-015 · A per-Run system prompt exists as `Update`, but no guide shows it.** Verdict: partly. There is no per-Run instruction field, but `Update: {"gotato.instruction": ...}` sets the Session's instruction as the Run's first write, `buildSession` re-reads it on every Run, `SkipSave` makes it last for one Run, and an empty value falls back to `Agent.Instruction` (code and FEATURES.md agree). It replaces, it does not append. Fix: a guide example; a test that pins the override (not checked whether one exists).

- [ ] **D-018 · A folded tool called before it is loaded costs the model a round.** Verdict: partly. Measured downstream in a staging run of 16 rounds: 2 of 36 tool calls hit `X was not loaded, so this call did not run. It is loaded now; call it again.` The message and the counts are documented (`search_tools` loads the top 3 and lists 5 more; both fixed; only `WithToolSearcher` changes the ranking). Wrong in the log: `search_tools` already tells loaded from listed (`Loaded: a, b.` and `Also found, not loaded: c, d.`); the model calls the listed names anyway. No decision records why a call is not run on the spot; a likely reason (a guess) is that a load takes effect with the Tool Result commit and the tool list must stay byte-stable for the cache. Their relief, `WithActiveToolSet`, is documented. Fix, one of: reword the listed line as an instruction ("not loaded yet: call `search_tools` with these names first"); for read-only tools, load and run on the refusal (changes the commit contract, needs a decision); add the `WithActiveToolSet` versus fold trade-off to FEATURES.md.
- [ ] **D-019 · No prompt-cache gain through a self-hosted gateway on the chat wire.** Verdict: mostly confirmed. Measured downstream: 16 rounds, 436k input tokens, no `cache_read_tokens` or `cache_write_tokens` in `usage`. The chat wire sends no `cache_control`; only `cache_key_field` and `cache_key_header` exist. `provider: anthropic` on the chat wire does **not** add `cache_control` (it only sets `anthropicCacheTTL` on the `anthropic-messages` wire). Usage parsing on chat reads `prompt_tokens_details.cached_tokens` and DeepSeek's `prompt_cache_hit_tokens`; it does not read the top-level `cache_read_input_tokens` or `cache_creation_input_tokens`, and `CacheWriteTokens` is never filled. Both fields are `omitempty`, so a missing field cannot tell "no hit" from "not reported" from "never cached". Whether the gateway in between injects `cache_control` cannot be checked here. Related to D-010. Fix: a FEATURES.md section on caching through a self-hosted gateway (inject at the gateway, or use the `anthropic-messages` wire with `provider: anthropic`); read the Anthropic-style usage fields on chat; sending `cache_control` on chat is a feature and needs a decision first.

- [ ] **D-020 · No warning that compaction is off when the context window is unknown.** Verdict: confirmed, overstated. A window of 0 means unknown, the gateway keeps no table of windows, and with no window and no `CeilingTokens` the ceiling trigger is off (code and FEATURES.md agree). No log, Event or start-up check says so; `inspect` drops the ceiling field when unknown; `gateway.example.yaml` fills in `context_window_tokens`, which reads as a required key. Wrong in the log: history does not grow until it fails; a refusal as too long still compacts once and retries, if `OverflowPhrases` recognises the wording (the built-in list is short on purpose, 400 and 413 only). Decision 038 argues against a conservative default ceiling ("a number that depends on the model"). Fix: warn once when the window is 0; show `ceiling=0` in `inspect`; an optional way to read the window from a gateway's model info (does not exist today); a loud line in FEATURES.md and the example config that no window means compaction only after a refusal.
- [ ] **D-021 · Parallel tools: a default that is easy to misread, and a hazard.** Verdict: partly. `MaxParallelTools` defaults to 1. Wrong in the log: at 1, `Sequential` changes nothing; it only matters above 1. Not in the log: `adapter/mcp` tools are not `Sequential`, so raising `MaxParallelTools` runs the server's **write** tools in parallel too, and grouping ignores `Effect`. The measured gain was small (about 7.6 s of 161.7 s). Fix: a FEATURES.md example (`MaxParallelTools: N`, write tools `Sequential`); say in the MCP section that adapter tools are not `Sequential`; an optional adapter switch that makes non-read tools `Sequential` (not a new default).
- [ ] **D-022 · No guide for asking a person before a tool runs.** Verdict: partly, the details hold. Decision 005 says no built-in approval and points to `PreToolUse` or a tool that hands the step to a person. `ToolUse` has `RunID`, `Turn`, `CallID`, `ToolID`, `Arguments`, `SourceIndex`, `Effect`, no Session id. `Before` runs for every call of the Turn before any executor starts. A wait inside `Before` is bounded by the Run's context and `RunTimeout`, not `ToolCallDeadline`. A `Before` that returns an error ends the Run (`CodeExtensionFailure`); to fail closed without that, return `Block:true`. A blocked call has `tool_ended` and no `tool_started` (kept on purpose: `tool_started` is a fact used on recovery). Fix: a "needs a person" section in `guides/extension-points.md` with those limits; add `SessionID` to `ToolUse` (new field, compatible). Keep the missing `tool_started`; tell blocked from failed through D-026.
- [ ] **D-023 · No guide for telling process text from the answer while streaming.** Verdict: partly. The order is `reply_started`, `text_delta` (sent only), `reply_ended` (stored, with `tool_calls` and `stop_reason`), then `tool_started`. `reply_ended` already says whether the reply asked for tools, and FEATURES.md and `examples/larkbot` use it ("the last reply of a Run is its final text"). A delta cannot say it earlier, because the model does not know yet. Fix: docs only: treat deltas as a draft, and on `reply_ended` fold the text when `tool_calls > 0`, keep it when 0. No new event field.
- [ ] **D-025 · Tool arguments are base64 in a Record.** Verdict: partly. `ToolUse.Arguments` and `ToolCall.Arguments` are `[]byte`, so JSON shows base64; no spec fixes that form. Changing to `json.RawMessage` is a break: arguments that are not valid JSON are stored on purpose (preflight checks `json.Valid`) and `RawMessage` would fail to commit them, and old Records hold base64 strings that would read as a JSON string. Fix without a break: keep `[]byte`; add an optional `arguments` JSON field (or a short summary) to `tool_started`; say in FEATURES.md that arguments are bytes, base64 in JSON.
- [ ] **D-026 · A failure's reason is only readable from text.** Verdict: partly. Blocked is already apart (`status: blocked`), and `Executed` tells "did not run" from "ran". `ToolResult` has no code; the reason is a `SafeError` prefix (`tool_resolution_failure:`, `tool_argument_failure:`, `tool_execution_failure:`, `deadline_exceeded:`), and a call to an unloaded tool is told by its `LoadedTools` and text. `tool_ended` does not carry `SafeError`, so a subscriber must read `tool_result_committed`. Fix: add `Code` (existing codes plus one for "not loaded") to `ToolResult` and `ToolEnded`, set where `rejectedPlan` builds the result. New field, compatible. Pairs with D-018.
- [ ] **D-024 · No default cap on Turns, tool calls or a Run's time in the core.** Verdict: confirmed, and by design (decision 038: a cap exists only for a named failure; one number does not fit a lookup and a long investigation). The 30-minute `RunTimeout` is in `service.Agent`, not in `CoreLimits`. `TurnStopper` is `Stop(ctx, TurnSnapshot) (StopDecision, error)` and `StopDecision` can only stop, not tell the model to wrap up. Fix, without a default: an optional helper `MaxTurns(n, ...)` and `MaxToolCalls(n)` built as a `TurnStopper`; "wrap up" before the cap needs a Notice, and whether a `TurnStopper` can send one was not checked.

- [ ] **D-027 · Where the time of a Run goes: the model, not the tools.** Verdict: confirmed by measurement (downstream, 2026-11-02, read-only, FAT; we did not check the raw data). 8 real Runs from the downstream Mongo Record. Model time (`turn_started` to `reply_ended`) is 81% to 99% of a Run; the sum of tool `elapsed_ms` is 0 to 17%; the rest (storage writes, commits) is 0.3% to 2.6%. No Run waited for a person. The 16-round Run: 161.7 s, 36 calls, model 143.0 s (88.5%), tools 17.2 s (10.7%), serial loss (sum minus max, per round) 7.7 s (4.8%). Per round the model time fits about 2.4 s fixed plus about 6.4 ms per output token; input from 5.6k to 49k tokens barely shows (12-round Run: 2.4 s to 5 to 6 s on the rounds that call tools). The slowest rounds are the last ones, with 1,000 or more output tokens (8 to 11 s). A call to a folded tool that was not loaded costs a whole extra round of 3 to 8 s (2 of 16 rounds in the 16-round Run, about 8% of it). The same output size took 13 to 17 s on three rounds of the 16-round Run and 4 to 6 s in a Run a day later; the cause is unknown (a guess: model or gateway jitter, not shown by this data). Not measured: cache hits (no `cache_read` field in `usage`), time to first token, and anything outside these 8 Runs. What this changes: raising `MaxParallelTools` (D-021) saves at most about 5%; a prompt cache (D-019) is a matter of cost, not shown to be a matter of latency; the wasted round of D-018 and the number of rounds (D-024) matter more. Fix: none in the core. Reword the "not loaded" line (D-018, round 2), put the measurement next to D-021 and D-019 in FEATURES.md ("parallel tools save little on this kind of Run"), and reopen the decision on a Turn cap (D-024) with this Run as the named failure. Ask the downstream team to find why the same output took twice as long on 10-29 (gateway side).

- [ ] **D-028 · A worked "ask a person" gate: what the downstream team built on `Before`.** Verdict: new evidence for D-022 (the guide it asks for does not exist yet). Source: the downstream log, 2026-10-29. Their gate blocks inside `Before` until a person clicks a card; read-only calls pass; a write goes through the card; any error blocks the call (fails closed, returns `Block:true`, never an error); who may click is a list of approvers, and an empty list refuses every write; at most 3 cards per answer; a refused call with the same arguments is not asked again; the total reply timeout was lengthened by 3 × 90 s so the wait does not run into it. 15 unit tests pass; the path that sends a card was **not** run on a real machine at the time of the log (only the refusal outside the list was). Fix: use this as the example in the "needs a person" section of `guides/extension-points.md` (D-022), with the card cap and the remembered refusal as the two choices a team makes; say the card path is unchecked against a live chat.
- [ ] **D-029 · A name prefix is not an Effect, and the downstream team already knows it.** Verdict: new evidence for D-004 and D-002. Their gateway shows 112 tools through one endpoint, named `<server_id>___<tool>` for 5 servers; they cut it into 5 ToolSets and strip the prefix (the case `WithToolFilter` and `WithToolRename` are for). Because the tools carry no annotations they know of (unchecked), they guess "read-only" from the start of the name (`get_`, `list_`, `search_`, `query_`, `describe_`, `read_`) plus `WithToolEffect` by exact name, and record the risk themselves: a `query_` tool can read production data and a name can hide a side effect; their plan before production is "refuse by default, allow an exact list". Fix: in the MCP section of FEATURES.md, say a name prefix is a guess and give "default `destructive`, then an exact list" as the safe form; use this 5-server cut as a test case for filter and rename.
- [ ] **D-030 · Waiting for the writer is a working answer to `not_writer`, for one replica.** Verdict: partly (new evidence, one pod in practice). Instead of forwarding to the writer (decision 024), the downstream team retries a `NotRun` after a back-off until the writer finishes, then takes the Session over. They run about one replica and did not test several pods writing one Session. Limit: a long Run (161.7 s in D-027) holds the second message that long. Fix: one paragraph in the multi-instance guide naming this as the plain option and its limit.
- [ ] **D-031 · Lark facts the example bot should list.** Verdict: facts of the host product, not defects of Gotato. From the downstream log: a card has a size limit (28 KB in their code, 30 KB in Lark's text); inline code shows as a black box, so they colour text instead; a pair of `*` that crosses a colour tag splits the tag and shows it; the thread key they use is the reply chain's `root_id`, then `parent_id`, then the message's own id; whether the bot may recall a card it sent depends on an app permission (unchecked). Fix: a "known pitfalls" list in `examples/larkbot/README.md`; no code.

- [ ] **D-032 · A tool cannot learn who asked, except through an unofficial route.** Verdict: confirmed by reading the code (2026-11-02). `RunRequest` has `SessionID`, `Agent`, `Prompt`, `Continue`, `Metadata`, `Update`, `SkipSave`, `Timeout` and `RequestID`. `Metadata` is applied only when a Session is created, `Update` writes Session metadata, `RequestID` goes only into `run_started`. `ToolUse` has `RunID`, `Turn`, `CallID`, `ToolID`, `Arguments`, `SourceIndex` and `Effect`, so `Before` and a tool get no asker. What does reach them is the caller's `ctx`: a value put in with `context.WithValue` before `Runner.Run` arrives in `Before` and in `Execute`; this is not documented anywhere. In a shared thread Session metadata is shared by every asker, while a ctx value lasts for one Run, and one Session runs one Run at a time, so askers do not mix. The downstream team's reminder tools need exactly this (the chat and the asker come from the message, never from the model). Fix: document the `ctx` route in `guides/extension-points.md` (with D-022 and D-028) and pin it with a test; decide whether a per-Run field that reaches `ToolUse` is worth a new field. This is a bigger answer to the need behind D-022 than `SessionID` alone.

- [ ] **D-033 · Follow-up to D-027: why the same output took twice as long, and a correction on input length.** Verdict: partly explained, by correlation (downstream, 2026-11-02, read-only, gateway dashboards; we did not check the raw data). The two Runs used the same model (`claude-haiku-5-5`), the same gateway setting (unchanged between them), no reasoning (`reasoning_bytes` 0 on every Turn), the same stop reasons, and no 429 or fallback on that model. The difference: in the window of the slow Run (10-29) another team was calling the same model through the shared gateway (about 24 of 40 requests); in the window of the fast Run (10-30) nobody was. Provider-side latency averaged 7.2 s against 4.3 s, and first-token latency 4.7 s against 3.2 s. Not shown: that the other team caused it (the "None" requests are ours only by count, not by key), nor the gateway's routing or queueing, which the downstream team cannot read. One comparison, small sample. **Correction to D-027**: input length does matter for first-token latency. In the fast Run it rose from 2.1 s to 4.4 s while the input grew from 5.6k to 49k tokens (about +2 s over 44k tokens), so "input length barely shows" is too strong; it is a part of the fixed cost per round, not the whole. Server-side first-token time can only be approximated (the Record keeps `reply_started` and the throttled `reply_part_kept`, no per-delta time). Fix: none in the core. Keep D-019 (a cache can lower first-token latency on a long prompt) as a latency item, not only a cost item, until measured; ask the gateway owners to split requests by key and show queueing.

- [ ] **D-034 · A long Run grew from 2.5K to 38.9K input tokens and never compacted mid-Run: the downstream context window was 0.** Verdict: **confirmed** as the downstream team's own setting, not a defect of Gotato (they read their code; not checked on a pod with `inspect`). Measured on 26 Runs and 86 Turns (2026-10-29 to 11-02): the longest Run went from 2.5K to 38.9K input tokens over 16 Turns and 36 calls (two more Runs grew 8.8 and 7.5 times); the growth comes from Tool Results, the largest about 31 KB, all under the 32 KiB spill page, so no spill and no `read_result` ever ran. Their 3 compactions were all `before_unload`, none `past_ceiling`. Cause: they build the gateway with five fields and no `ContextWindowTokens`, and set no `CompactPolicy.CeilingTokens`, so the ceiling trigger is off (this is D-020). Decided with them: no configurable spill threshold (a spill costs a `read_result` call, and a call costs a round, which D-027 shows is the expensive part); clearing old Tool Results in the middle of a Run is **not built** and is a decision to write first, because the Message that stays is written once so the bytes already sent do not change (decisions 034 and 040). Fix: none in the core. The downstream team sets the window or `CeilingTokens` and looks for `past_ceiling`; D-020's warning is the way a team learns of this sooner.
- [ ] **D-035 · Observability: `compaction_ended` has no ceiling or window, and `context_built` has no per-part size.** Verdict: confirmed by reading `ContextBuilt` and FEATURES.md (suggestion, not a defect). `ContextBuilt` carries `strategy`, `messages`, `source_messages`, `selected_messages`, `prefix_hash`, `prefix_messages`, `system_bytes` and `tools`; the sizes before and after a compaction are bytes ÷ 4. A team cannot tell how far a Session is from its ceiling from the Record. Fix, in two compatible steps agreed with the downstream team: add the ceiling and the window to `compaction_ended`; then add an estimate per part (system, tool catalog, history, Tool Results) to `context_built`, named an estimate. `inspect` already shows the ceiling for a Turn (D-020).
- [ ] **D-036 · Decision wanted: clearing old Tool Results in the middle of a Run.** Not a finding of a defect. Gotato has compaction (a Segment, written once) and spill (a page over 32 KiB) and nothing between them. A mechanism that hides old results from later requests would change bytes the provider already cached (decisions 034, 040). The measured cost of a long input is about +2 s of first-token time over 44k tokens (D-033), so the gain in latency is bounded; the gain in money is not measured. Write the decision, and decide whether the compaction ceiling (D-034) already answers it, before any code.

- [ ] **D-037 · `search_tools` with `toolset` returns a whole folded ToolSet, with no size cap, and it stays in the Context.** Verdict: **confirmed by data**, by design (follow-up to D-011: the catalog has no size budget). Measured downstream on 17 `search_tools` calls: 6 were over 8 KiB serialized, all with `toolset` (the largest: a pure `toolset` call, 30,349 B serialized and 15,020 B of text, for an alarm ToolSet; others 25,397 B, 16,315 B, 13,589 B, and two mixed with `queries` at 17,341 B and 15,588 B). Calls with only `queries` were at most 2.1 KB, with only `names` at most 1.2 KB. All are under the 32 KiB spill page, so none is spilled and each stays in every later request (adds to D-034). The serialized form is about twice the text because the result also carries `loaded_tools`; by reading `gateway`, that list is turned into a request only on the wires with native deferred loading (`gateway/deferred.go` returns early unless the wire has it; `chat.go` does not use `LoadedTools`), so on the chat wire it is stored in the Record and not sent (read the code, not run). Fix: none needed in the core. In FEATURES.md and the tool-search guide: say that `toolset` lists every tool of a ToolSet with its description, that the result is not capped and not spilled, and that `queries` or `names` are the cheap forms; optionally a size budget for a listing as a later decision. The downstream team tells the model to prefer `queries` and `names`.
