### New since the first pass


- [ ] **D-018 · A folded tool called before it is loaded costs the model a round.** Verdict: partly. Measured on a real service built on Gotato, in a run of 16 rounds: 2 of 36 tool calls hit `X was not loaded, so this call did not run. It is loaded now; call it again.` The message and the counts are documented (`search_tools` loads the top 3 and lists 5 more; both fixed; only `WithToolSearcher` changes the ranking). Not so: `search_tools` already tells loaded from listed (`Loaded: a, b.` and `Also found, not loaded: c, d.`); the model calls the listed names anyway. No decision records why a call is not run on the spot; a likely reason (a guess) is that a load takes effect with the Tool Result commit and the tool list must stay byte-stable for the cache. The relief, `WithActiveToolSet`, is documented. Fix, one of: reword the listed line as an instruction ("not loaded yet: call `search_tools` with these names first"); for read-only tools, load and run on the refusal (changes the commit contract, needs a decision); add the `WithActiveToolSet` versus fold trade-off to FEATURES.md.
- [ ] **D-019 · No prompt-cache gain on the chat wire.** Verdict: mostly confirmed. Measured on a real service built on Gotato: 16 rounds, 436k input tokens, no `cache_read_tokens` or `cache_write_tokens` in `usage`. The chat wire sends no `cache_control`; only `cache_key_field` and `cache_key_header` exist. `provider: anthropic` on the chat wire does **not** add `cache_control` (it only sets `anthropicCacheTTL` on the `anthropic-messages` wire). Usage parsing on chat reads `prompt_tokens_details.cached_tokens` and DeepSeek's `prompt_cache_hit_tokens`; it does not read the top-level `cache_read_input_tokens` or `cache_creation_input_tokens`, and `CacheWriteTokens` is never filled. Both fields are `omitempty`, so a missing field cannot tell "no hit" from "not reported" from "never cached". Related to D-010. Fix: a FEATURES.md section on caching on the chat wire (add `cache_control` at the endpoint, or use the `anthropic-messages` wire with `provider: anthropic`); read the Anthropic-style usage fields on chat; sending `cache_control` on chat is a feature and needs a decision first.

- [ ] **D-020 · No warning that compaction is off when the context window is unknown.** Verdict: confirmed, overstated. A window of 0 means unknown, Gotato keeps no table of windows, and with no window and no `CeilingTokens` the ceiling trigger is off (code and FEATURES.md agree). No log, Event or start-up check says so; `inspect` drops the ceiling field when unknown; `gateway.example.yaml` fills in `context_window_tokens`, which reads as a required key. Not so: history does not grow until it fails; a refusal as too long still compacts once and retries, if `OverflowPhrases` recognises the wording (the built-in list is short on purpose, 400 and 413 only). Decision 038 argues against a conservative default ceiling ("a number that depends on the model"). Fix: the warning is dropped (see decision 042). Done: `inspect` shows `ceiling=0`, and a loud line in FEATURES.md and the example config says that no window means compaction only after a refusal.
- [ ] **D-025 · Tool arguments are base64 in a Record.** Verdict: partly. `ToolUse.Arguments` and `ToolCall.Arguments` are `[]byte`, so JSON shows base64; no spec fixes that form. Changing to `json.RawMessage` is a break: arguments that are not valid JSON are stored on purpose (preflight checks `json.Valid`) and `RawMessage` would fail to commit them, and old Records hold base64 strings that would read as a JSON string. Fix without a break: keep `[]byte`; add an optional `arguments` JSON field (or a short summary) to `tool_started`; say in FEATURES.md that arguments are bytes, base64 in JSON.
- [ ] **D-024 · No default cap on Turns, tool calls or a Run's time in the core.** Verdict: confirmed, and by design (decision 038: a cap exists only for a named failure; one number does not fit a lookup and a long investigation). The 30-minute `RunTimeout` is in `service.Agent`, not in `CoreLimits`. `TurnStopper` is `Stop(ctx, TurnSnapshot) (StopDecision, error)` and `StopDecision` can only stop, not tell the model to wrap up. Fix, without a default: an optional helper `MaxTurns(n, ...)` and `MaxToolCalls(n)` built as a `TurnStopper`; "wrap up" before the cap needs a Notice, and whether a `TurnStopper` can send one was not checked.



- [ ] **D-032 · A tool cannot learn who asked, except through an unofficial route.** Verdict: confirmed by reading the code (2026-11-02). `RunRequest` has `SessionID`, `Agent`, `Prompt`, `Continue`, `Metadata`, `Update`, `SkipSave`, `Timeout` and `RequestID`. `Metadata` is applied only when a Session is created, `Update` writes Session metadata, `RequestID` goes only into `run_started`. `ToolUse` has `RunID`, `Turn`, `CallID`, `ToolID`, `Arguments`, `SourceIndex` and `Effect`, so `Before` and a tool get no asker. What does reach them is the caller's `ctx`: a value put in with `context.WithValue` before `Runner.Run` arrives in `Before` and in `Execute`; this is not documented anywhere. In a shared thread Session metadata is shared by every asker, while a ctx value lasts for one Run, and one Session runs one Run at a time, so askers do not mix. A reminder tool needs exactly this (the chat and the asker come from the message, never from the model). Fix: document the `ctx` route in `guides/extension-points.md` (with D-022) and pin it with a test; decide whether a per-Run field that reaches `ToolUse` is worth a new field. This is a bigger answer to the need behind D-022 than `SessionID` alone.

- [ ] **D-033 · Follow-up to D-027: a correction on input length.** Verdict: confirmed by measurement (2026-11-02, read-only; we did not check the raw data). **Correction to D-027**: input length does matter for first-token latency. In the fast Run it rose from 2.1 s to 4.4 s while the input grew from 5.6k to 49k tokens (about +2 s over 44k tokens), so "input length barely shows" is too strong; it is a part of the fixed cost per round, not the whole. The same output size took different time on two days (same model, no reasoning, same stop reasons); no cause is shown by the data. Server-side first-token time can only be approximated (the Record keeps `reply_started` and the throttled `reply_part_kept`, no per-delta time). Fix: none in the core. Keep D-019 (a cache can lower first-token latency on a long prompt) as a latency item, not only a cost item, until measured.

- [ ] **D-034 · A long Run grew from 2.5K to 38.9K input tokens and never compacted mid-Run.** Verdict: **confirmed**, as the effect of a model window left unset, not a defect of Gotato (read in code; not checked on a pod with `inspect`). A Session whose model window is left unset never compacts mid-Run; measured: input grew from 2.5K to 38.9K tokens over 16 Turns and 3 compactions were all `before_unload`. Measured on 26 Runs and 86 Turns (2026-10-29 to 11-02): the longest Run went from 2.5K to 38.9K input tokens over 16 Turns and 36 calls (two more Runs grew 8.8 and 7.5 times); the growth comes from Tool Results, the largest about 31 KB, all under the 32 KiB spill page, so no spill and no `read_result` ever ran. None of the compactions was `past_ceiling`: with no `ContextWindowTokens` and no `CompactPolicy.CeilingTokens`, the ceiling trigger is off (this is D-020). Decided: no configurable spill threshold (a spill costs a `read_result` call, and a call costs a round, which D-027 shows is the expensive part); clearing old Tool Results in the middle of a Run is **not built** and is a decision to write first, because the Message that stays is written once so the bytes already sent do not change (decisions 034 and 040). Fix: none in the core. Set the window or `CeilingTokens` and look for `past_ceiling`; D-020's warning is the way a team learns of this sooner.
- [ ] **D-035 · Observability: `compaction_ended` shows no window and hides a ceiling of 0, and `context_built` has no per-part size.** Verdict: partly (suggestion, not a defect; corrected on 2026-11-02 after reading the code). The `Compaction` value a `compaction_ended` carries already has `ceiling_tokens`, but it is `omitempty`, so a ceiling that is off (0) is left out and cannot be told from "not recorded", and it is not set on a merge Checkpoint; there is no window field at all. `ContextBuilt` carries `strategy`, `messages`, `source_messages`, `selected_messages`, `prefix_hash`, `prefix_messages`, `system_bytes` and `tools`; the sizes before and after a compaction are bytes ÷ 4. A team cannot tell how far a Session is from its ceiling from the Record. Fix, in two steps: add `window_tokens` and write `ceiling_tokens` even when 0 (a JSON shape change, to be listed in CHANGELOG), set on every Checkpoint including a merge; this needs the two numbers carried to `Record.checkpointLocked`, whose three public callers (`CloseSegmentAndCheckpoint`, `MergeSegments`, `CheckpointSegments`) then take a settings argument, so it is a change to a public API and wants a decision first; then add an estimate per part (system, tool catalog, history, Tool Results) to `context_built`, named an estimate. `inspect` already shows the ceiling for a Turn (D-020).
- [ ] **D-036 · Decision wanted: clearing old Tool Results in the middle of a Run.** Not a finding of a defect. Gotato has compaction (a Segment, written once) and spill (a page over 32 KiB) and nothing between them. A mechanism that hides old results from later requests would change bytes the provider already cached (decisions 034, 040). The measured cost of a long input is about +2 s of first-token time over 44k tokens (D-033), so the gain in latency is bounded; the gain in money is not measured. Write the decision, and decide whether the compaction ceiling (D-034) already answers it, before any code.


- [ ] **D-038 · A compaction ceiling is a hard failure line, and a low one ends Runs.** Verdict: confirmed by measurement and by reading the code (2026-11-02). Measured on a real service with `CeilingTokens` set to 30,000 and no Recap writer: a Run of 7 Turns and 20 tool calls compacted twice (`past_ceiling`), the second time from about 35K estimated tokens to about 22K by the Record's figure, and then ended `limit_exceeded: the Context is still past the ceiling after its compaction (about 30046 tokens, ceiling 30000)`. Without a Recap a compaction shrank the Context by only 18% to 37%, and one large Tool Result in the last Turn (spilled) pushed it back to the ceiling. By the code (`modelctx/auto_compact.go`): the check before a compaction uses the usage the provider last reported plus an estimate of what came after, or an estimate of the Messages plus the request overhead; the check after the compaction is a fresh estimate of the Messages plus `requestOverhead` (instruction and tool definitions, bytes over 4), and the Run ends `limit_exceeded` if it is still over, if the compaction failed, or if there was nothing to compact. The two figures differ because the Record's figure is a size of the Messages and the error's figure adds the overhead of the instruction and the tool definitions (a gap of about 8K tokens here); this is read from the code, the exact field of the Record's figure was not traced. The last Turn is always kept, so a big last Turn cannot be compacted away. The failure is documented (FEATURES.md and specs/compaction.md say a Context still past the ceiling ends the Run `limit_exceeded`) but nowhere is it said that a ceiling set below the window makes a Run fail, nor how low is too low. Fix: say in the compaction section that the ceiling is a hard line, not a cost knob, and that it must stay above the baseline after a compaction (overhead of the instruction and tools, the kept tail of up to a quarter of the ceiling, a Recap if any) plus the largest Tool Result the Run can hold in one Turn (below the 32 KiB spill page, so up to about 8K tokens); the last part is a rule of thumb, not measured. Decide separately whether a ceiling the team set below the window should end a Run, or only compact and go on until the provider refuses (decision 038 ties the ceiling to the window, where ending is right; a lower, team-set ceiling is a different use).
- [ ] **D-039 · After a compaction, a loaded tool the Session never called is unloaded, and its first call fails once.** Verdict: **confirmed by measurement**, expected behavior and not a defect (checked in the Record of a real Run). After a compaction on a real service the next Turn made 5 calls to tools that returned `was not loaded, so this call did not run`, and the following Turns called them again successfully. FEATURES.md says the tools the closed Segment called and the kept tail calls stay loaded and the others unload (`tool_unloaded`), and that on the list form a load costs a cache read, which is why tools unload at a compaction and nowhere else; a tool of an active ToolSet never unloads. So a compaction can cost one Turn when the model calls a tool it only found, never used. Measured: at the first compaction the Session kept 3 tools that had really been called and wrote 23 `tool_unloaded` (`why: compaction`) for every tool that had only been loaded through `search_tools`; the 5 tools whose first call failed had been loaded in Turns 1 to 3, never started, and were all in that batch; the call failed once and succeeded after the next load, at the cost of one idle Turn. The second compaction kept 8 and unloaded 1. The failed call's text already says `It is loaded now; call it again.`; loading and running it on the spot is the second half of D-018. Fix: one sentence in the compaction and tool-search sections that a compaction can unload tools and the next call to one costs a round; `WithActiveToolSet` keeps a set loaded. Pairs with D-018.
